# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- JSON format, version 1 (`spec/json-format.md`), the contract between
  languages: documents with `"version": 1`, the encoding of values (exact
  64-bit integers, floats with `{"$float": "inf"}`, `{"$decimal": ...}`,
  `{"$date": ...}` and `{"$datetime": ...}` with fixed offsets or RFC 9557 time
  zones, lists and maps), every condition node, canonical writing, error codes
  and limits. JSON Schemas in `spec/schemas/v1/`, checked against valid and
  invalid examples. The specification moved from `docs/spec/` to `spec/`.
- JSON format: rules (`name`, `when`, payload `then`, `priority`, `tags`,
  `description`, `metadata`) and rule sets (`hit_policy`, `aggregate`, `logic`,
  `strict`, `rules`), with JSON Schemas and the error codes
  `rule_definition_error`, `registry_error` and `unsupported`. Payload member
  order is significant. Actions are not serialized yet (writers take
  `omit_actions`), and rule metadata values must be data values.
- JSON format: decisions, with every rule's result tree (`truth` for
  conditions, `value` for values), structured reasons and the selected rules;
  outputs are derived from the payload trees. A decision is read with its rule
  set and checked against it node by node (`decision_mismatch`).
- Error catalogue (`spec/errors.md`): stable codes, the hierarchy under
  `CleanRulesError`, and the context fields that conformance vectors compare.
- Conformance vectors (`conformance/`): the vector format and its JSON Schema,
  a checker, 125 hand-picked and 1,821 generated vectors exported from the Python v1,
  and 187 vectors for
  reading documents, written from the spec.
- Data model (`spec/data-model.md`): values, decimals of 38 digits (as Arrow
  `Decimal128`), microsecond datetimes, opaque values for native data with no
  equivalent, nulls with a reason (`int_overflow`, the new `decimal_overflow`,
  `read_error`), and how each language's data is read and converted.
- Specification of explanations and summaries (`spec/explain.md`): rule
  status, requirements with `all`/`any` groups, simplification, the check that
  each way to fire really works, counterfactuals and notes. Their JSON forms
  are output-only documents.
- Specification: `matches` patterns use the syntax of Rust's `regex` crate, and
  a null constant is only allowed as the operand of `is_null` (also under
  `and`, `or` and `not`).
- YAML rule files (`spec/json-format.md`, *YAML*): the JSON subset of the YAML
  1.2 core schema, one document, no directives, anchors, aliases or tags,
  errors with line and column, and a 1 MiB default size limit of their own;
  38 new conformance vectors. Rust core: the `yaml` feature (`cleanrules::yaml`
  with `parse` and `to_string`, `format::read_yaml_document` and
  `format::read_yaml_decision_document`), `Limits::max_yaml_size`, and
  `read_parsed_document`/`read_parsed_decision_document` for documents already
  parsed.
- Python binding: `loads`, `load`, `dumps` and `dump` read and write
  conditions, rules and rule sets as JSON or YAML documents, from strings,
  bytes, paths or open files.
- Text syntax for conditions, rules and rule sets (`spec/text.md`):
  `RULE vip PRIORITY 10 IF customer.years > 5 THEN discount = 0.15`, with
  `AND`/`OR`/`NOT` (and `&`, `|`, `~`, as in fuzzytool), comparisons, `IN`,
  `BETWEEN`, `IS [NOT] NULL`, `MATCHES`, `STARTS WITH`, `ENDS WITH`,
  `CONTAINS`, arithmetic, typed literals (`DATE "…"`, `DECIMAL "…"`) and rule
  set headers (`HIT POLICY`, `AGGREGATE`, `LOGIC`, `STRICT`). Errors carry the
  line and column; every condition, rule and rule set without metadata has a
  canonical text that reads back as the same model. Rule files use the suffix
  `.rules` and have a 4 MiB default size limit. 86 new conformance vectors.
  Rust core: `cleanrules::text::{parse, parse_rule, to_string}`, `Display` for
  `Node`, and `Limits::max_text_size` (a new public field of `Limits`).
- Python binding: `format="text"` in `loads`, `load`, `dumps` and `dump`
  (`.rules` files), and `rule_from_text`, which reads one rule and can attach
  an action to it.
- Text of explanations and summaries (`spec/explain.md`, *Text* and
  *Summaries*), generated by the core and the same in every language:
  conditions, names and constants as in the canonical text, data values
  bounded (long strings, lists and maps are cut), gaps as plain numbers, days
  or durations. The canonical text writes a float as plain digits followed by
  `e0` when its magnitude is 0 or within [1e-4, 1e16) (`0.7e0`, not `7e-1`).
  Rust core: `Display` for `Explanation`, `RuleExplanation`, `Cause` and
  `Summary`, fixed by snapshot tests (`insta`); `RuleExplanation::rule` is now
  the rule (`&Rule`), not its name; `Summary::actions` and
  `Summary::with_actions`, which bindings use, and summaries in JSON mark a rule
  with an action (`"action": true`), as the spec said. The explanation and
  summary structs are `#[non_exhaustive]`: only `explain` and `summary` build
  them.
- Decision tables (`spec/tables.md`): inputs, outputs with optional output
  values, and rows whose cells use the text syntax without their column
  (`> 5`, `IN ('ES', 'PT')`, `-`). A table is read and written as a JSON or YAML
  document (`"decision_table"`, added to format version 1 with its JSON
  Schema) and as CSV (RFC 4180; commas, semicolons or tabs; settings lines
  `HIT POLICY`, `AGGREGATE`, `LOGIC`, `STRICT`, DMN letters such as `P` and
  `C+`; `RULE`, `PRIORITY`, `DESCRIPTION` and `THEN` columns), with errors
  located by line and column or JSON Pointer. It compiles into a rule set: the
  new `output_order` policy and `priority` rank rows by their output values, as
  in DMN. Reading a table is bounded by a count of cells and condition nodes
  (`Limits::max_table_size`, 2²¹ by default), since every input cell holds a
  copy of its column. 99 conformance vectors. Rust core: `cleanrules::table`
  (`DecisionTable` with `new`, `from_csv`, `to_csv` and `ruleset`,
  `TableConfig`, `TablePolicy`, `TableOutput`, `TableRow`),
  `Document::DecisionTable` and `format::write_table`. `RuleSet::new` checks
  rule names in `O(n log n)`.
- Python binding: `DecisionTable`, `TablePolicy`, `TableOutput` and
  `TableRow`; `format="csv"` and `.csv` files in `load`, `loads`, `dump` and
  `dumps`, which also read and write tables as JSON and YAML; `table.ruleset`
  (built on first use), `evaluate`, `evaluate_many` and `summary`. Tables are
  immutable and pickle. `load` and `dump` keep line breaks as written in every
  format, on every platform.
- Decision tables from grids (`spec/tables.md`, *Grids*): a header and rows of
  cells, as spreadsheets and data frames hold them. Text cells are read as CSV
  fields, other values as constants (equality under an input), and nodes built
  in a host language as they are; errors point into the grid (`/header/<c>`,
  `/rows/<r>/<c>`). An output cell written as a bare name that is one of its
  column's string values (`high` for `'high'`) gets a hint to quote it. 28
  conformance vectors, with the new `table_grid` input. Rust core:
  `DecisionTable::grid` and `GridBuilder` (`push_row`, `finish`), which build a
  table one row at a time, `DecisionTable::from_grid`, `table::HeaderItem` and
  `table::Cell`.
- Actions by registered name (`spec/rules.md`, *Actions*): a rule may name its
  action (`"do": "notify"` in JSON and YAML, `DO notify` in text), which is
  data: read, written and shown in summaries (`"do"` next to `"action": true`;
  `DO notify` in the text). The core never resolves or runs it. Bindings look
  names up only in a registry the caller supplies, never as import paths; an
  unknown name is a `registry_error` raised before anything runs. `DO` is now
  a keyword of the text syntax: a field named `do` is written `` `do` ``.
  16 conformance vectors. Rust core: `Rule::action_name`,
  `Rule::get_action_name` and `RuleSet::check_action_names`, which every
  binding uses to report an unknown or unbound name the same way.
- Python binding: `Rule(do="notify")` names an action, and `Rule.action_name`
  gives the name; `RuleSet.bind(actions)` resolves names in a mapping of callables,
  and `load`, `loads` and `rule_from_text` take `actions=`. `run` refuses a
  rule set with unbound names before evaluating. Named actions are written
  with their rules; only an action given as code without a name needs
  `omit_actions`. `RuleSummary.action_name` gives the name. A malformed
  registry is a `TypeError`.
- Python binding: `DecisionTable(header, rows, ...)` builds a table from rows,
  and `DecisionTable.from_dataframe` from a pandas or polars `DataFrame`
  (neither is imported; missing values are empty cells). A `str` cell is the
  text syntax, as in the table's CSV. `HeaderItem` types a header. `TableOutput`
  values default to none, and `load`, `loads` and the constructors take
  `max_table_size`.
- Python binding: `str()` of an `Explanation`, a `RuleExplanation`, a `Cause`
  and a `Summary` gives that text, and `str()` of a condition its canonical
  text (`x > 5 AND NOT vip`; `repr()` is still the Python that builds it).
  `RuleSummary.action`, and `Summary.to_dict()` marks rules with an action.
  The text is made on first use, so `explain()` costs nothing more.
- Python binding, safety: frames, tracebacks, code objects, generators,
  coroutines and functions in the data are opaque; a rule can no longer reach
  the program's globals or locals through them. Decisions in reference cycles
  are freed by the garbage collector. `ActionContext.tree` gives the result
  tree of the rule's condition.
- Rust core and spec: a read error met in the middle of a path gives
  `read_error` (and raises in strict mode) instead of an ordinary null;
  `Error::unsupported` sets `operation` and `reason`.
- Python binding: `evaluate_tree` and `evaluate_value_tree` evaluate one node
  and return its `ResultTree` (`spec/ast.md`, *Evaluating one node*).
- Python conformance runner: every vector runs through the binding's JSON
  entry points and, except the `read` vectors, with native Python data and the
  Python API; all pass.
- Python binding: actions (`Rule(..., do=...)`) and `RuleSet.run`, which runs
  the actions of the selected rules in order with an `ActionContext` and stops
  at the first that raises with `ActionError`. `Rule` and `RuleSet` pickle and
  copy. The public API is fully typed (`pyright --verifytypes`).
- Python binding: numpy and pandas values: numpy scalars, `datetime64` (a
  naive datetime, truncated to the microsecond), arrays as lists, `NaT`,
  `pandas.NA` and `pandas.NaT` as nulls, `Timestamp`s, and pandas rows from
  `iterrows()` and `itertuples()`.
- Python binding: input data is read as `spec/data-model.md` says: only the
  paths a rule set reads, each object once; mappings, records (namedtuples,
  objects with `keys()` such as pandas rows), sequences and objects' public
  data attributes (dataclasses, attrs, Pydantic, properties), never private
  names, methods, classes or modules. A getter that raises gives `read_error`,
  and strict mode chains the original exception. Opaque values come back as
  the same object.
- Rust core: records, maps whose entries also have positions (`Map::record`),
  read by key and by position.
- Errors carry the context fields `node` (the operand that broke a
  construction rule, or the innermost node whose evaluation failed),
  `operation` and `reason` (`spec/errors.md`), in the Rust core and in Python,
  where `node` is an `Expr` and appears in the message.
- Python binding: `Rule`, `RuleSet` (a sequence of rules by position and by
  name), `HitPolicy`, `Aggregate`, `Truth`, `Status`, `Decision` (`results`,
  `selected`, `fired`, read-only `outputs` and `output`, `aggregated`,
  `explain()`, `why_not()`, `to_dict()`), `RuleResult`, `Explanation`,
  `RuleExplanation`, `Cause`, `CauseGroup`, `Reason`, `Counterfactual`, `Note`,
  `Summary`, `FieldUsage` and `RuleSummary`, evaluated and explained by the
  core. Explanations hold Python values (gaps are numbers or `timedelta`s).
  Input data is converted whole for now (dicts, lists and scalars), with a
  depth limit and cycle detection. Rule sets can be shared by threads, also on
  free-threaded Python; evaluation releases the GIL.
- Python binding: conditions built with `F`, `Field`, `Const`, operators and
  methods (`is_in`, `between`, `is_null`, `matches`, `starts_with`,
  `ends_with`, `contains`, `abs`), with the v1's guards against Python
  pitfalls and a `repr` that is Python source; every construction rule is
  checked by the core. The exception hierarchy of `spec/errors.md`
  (`cleanrules.CleanRulesError` and its subclasses, with codes and context).
  Nodes pickle through the JSON format.
- Rust core: `AwareDateTime::from_native` builds an aware datetime from a
  native one as `spec/data-model.md` says, and the crate re-exports `jiff`.
- Python binding scaffold (`bindings/python`, PyO3 and maturin): the
  `cleanrules` package with its native module, `__version__` and
  `FORMAT_VERSION`. Wheels: `abi3` for CPython 3.11+, `cp314t` for
  free-threaded 3.14, and `abi3t` for CPython 3.15+; the module supports free
  threading. CI builds and tests the wheels and the sdist (not published yet).
- Benchmark comparison with zen-engine (`benchmarks/zen`), on the same rules
  as a zen decision table, after checking that both engines select the same
  rules for every input.
- Benchmarks of the Rust core (`criterion`, `crates/core/benches/`): the `eval`
  and `explain` suites over a shared loan screening workload, with the first
  results in `benchmarks/results/`.
- Property tests of the Rust core (`proptest`): non-strict evaluation never
  fails and gives a reason exactly for unknown truths and null values; strict
  mode agrees or raises an evaluation error; De Morgan and double negation
  hold on evaluation; conditions round-trip through JSON; every decision reads
  back; and explanation causes all hold for selected rules, none hold for
  achievable rules that did not fire, and are all unknown for unknown ones.
- `cleanrules::explain`: explanations (status, `all`/`any` requirements,
  simplification, options checked to make the rule fire, causes with the values
  read, counterfactuals with exact gaps, notes) and summaries, with their JSON
  forms. The conformance runner passes all 317 explanation and 3 summary vectors.
- `cleanrules::format::read_decision_document`: decisions read with their rule
  set, rebuilt into a `Decision` and checked as `spec/json-format.md` requires
  (`decision_mismatch`).
- `cleanrules::rules`: rules, rule sets, the six hit policies, payloads,
  aggregates, batches and decisions; rule and rule set documents, and decisions
  written in JSON. The conformance runner passes all 302 evaluation vectors.
- `cleanrules::eval`: the evaluator, generic over the logic, with result
  trees, structured reasons, exact comparisons, 64-bit overflow, and strict
  mode; result trees in JSON (`format::write_result`). The core's conformance
  runner passes all 1,326 condition and value vectors.
- `cleanrules::logic`: the `Logic` trait, Kleene's three-valued logic
  registered as `"boolean"`, and lookup by name with `registry_error`.
- `cleanrules::build`: idiomatic Rust construction of conditions, with
  methods for comparisons and tests, operators for connectives and arithmetic,
  and the first construction error reported by `.build()`.
- `cleanrules::ast`: the condition AST, valid by construction, with the
  construction rules of `spec/ast.md`, structural identity and field paths.
- `cleanrules::format::read_document` and `write_document` for condition
  documents, with the error order and locations of the spec.
- `cleanrules::format::value`: values in JSON, read as constants, data or
  recorded values and written in canonical form, including datetimes with
  fixed offsets or IANA time zones checked against the bundled database.
- `cleanrules::json`: a strict JSON reader and writer that keeps member order
  and number literals, rejects duplicate keys, lone surrogates and byte order
  marks, reports errors by line and column in code points, enforces size and
  nesting limits, and never overflows the stack.
- Core value model: `Value` (null with a reason, booleans, ints, floats,
  38-digit decimals, strings, dates, naive and aware datetimes, lists, maps,
  opaque values), exact comparison across ints, floats and decimals, type
  groups, equality under `ANY`, and the core `Error` with the stable codes of
  `spec/errors.md`.
- Rust workspace with the core crate `cleanrules` (edition 2024, MSRV 1.95):
  strict lints (no `unsafe`, clippy pedantic, no `unwrap` or printing in
  library code), rustfmt, cargo-deny, and CI on Linux, macOS and Windows.
- Repository skeleton: README, MIT license, changelog, `.gitignore`.
- Development roadmap (`docs/PLAN.md`) and Claude Code project configuration
  (`CLAUDE.md`, `.claude/`).

### Changed

- The text syntax reserves `DO` (task D.4): a field, key or rule named `do`,
  in any case, is now written between backticks or quotes.
- `Summary::with_actions` adds the rules whose action is code to those that
  name theirs, which the core marks itself, instead of replacing every flag.
- Strict-mode errors write a field's path as the text syntax does
  (`missing field items[2].price`, not `items.[2].price`), as explanations
  already did (task D.5).

### Removed

- The Python v1 (`rulepy`), its tests, its documentation site and the
  temporary vector exporter (task A.4). Its semantics live on in `spec/` and
  `conformance/`, and the code in the git tag `python-reference`; the section
  below lists what it contained. The Python package comes back as a binding of
  the Rust core in phase C, under the name `cleanrules`.

## [python-reference] - not released

The Python v1, kept in the git tag `python-reference`.

### Added

- Package metadata (`pyproject.toml`, hatchling, `src/` layout): Python >= 3.11,
  no runtime dependencies, optional extras `fuzzy`, `polars`, `pandas`, `yaml`,
  `audit`, `ml`, `fast` and `bench` reserved for upcoming features.
- `rulepy.errors` (also exported from `rulepy`): `RulePyError` base class with an
  optional `hint`; `UnsupportedOperation` (also a `NotImplementedError`) naming
  the operation, backend, rule and node; `RuleSyntaxError` (also a `ValueError`)
  reporting 1-based line/column with a caret under the offending line;
  `EvaluationError` naming the rule and node. All errors pickle with their
  attributes intact.
- `ExpressionError` (also a `TypeError` and `ValueError`) for malformed
  condition trees, with optional rule and node context.
- `rulepy.core.expr`: immutable condition AST with `Field("a", 0, "b")`,
  `Const` (normalizes numpy/Enum/subclass scalars; rejects NaN and integers
  beyond 64 bits), `Compare`, n-ary flattened `And(*conditions)` and
  `Or(*conditions)`, and `Not`. `Const` also keeps `Decimal` values exact (for
  money and rates), rejecting `Decimal` NaN. Trees are checked when built, can
  be walked, compared with `same_as()` and keyed with `structural_key()`, and
  pickle.
- More condition nodes: `In` (canonical sorted set of same-type values),
  `Between` (polars-style `closed`), `IsNull`, `Matches` (regex search),
  `StringTest` (`starts_with` / `ends_with` / `contains`, literal text) and
  arithmetic (`Arith` with `add` / `sub` / `mul` / `div`, `Abs`, `Neg`), with
  the type aliases `StringOp`, `ArithOp` and `Closed`.
- `F` (exported from `rulepy`) for writing conditions in Python:
  `(F.customer.age >= 18) & F.country.is_in({"ES", "PT"}) & ~F.blocked`,
  `F["key with spaces"]`, `F.orders[0].total`. Comparison, logical (`&`, `|`,
  `~`) and arithmetic operators build nodes, as do the methods `is_in`,
  `between`, `is_null`, `matches`, `starts_with`, `ends_with`, `contains` and
  `abs`.
- Nodes guard against Python pitfalls with a clear `ExpressionError`:
  `and`/`or`/`not`, `if node:`, chained comparisons, `== None`, Python bools
  next to `&`/`|`, iterating a node, numpy arrays and pandas objects as
  operands, polars-style namespaces, and calling a field path (with a "did you
  mean" hint). Nodes hash by identity.
- `repr()` of a condition is Python that rebuilds the same tree.
- "Common pitfalls" documentation page.
- `rulepy.core.logic`: `Truth` (ordered `FALSE < UNKNOWN < TRUE`, not usable as a
  Python bool), the `Logic` protocol (provisional until 1.0), the optional
  `GradedLogic` protocol, and `BooleanLogic` (Kleene three-valued logic), with
  a registry (`get_logic(name, **params)`, `register_logic`,
  `unregister_logic`, `logic_names`).
- `rulepy.core.evaluate`: the reference evaluator. `evaluate(condition, data)`
  returns a truth value; `evaluate_tree` returns a `NodeResult` tree with a
  structured `Reason` (code, field paths, type groups) wherever a value is
  `UNKNOWN` or null; `evaluate_value` evaluates fields and arithmetic. It reads
  mappings, sequences, records, pandas rows, dataclasses, Pydantic models and
  numpy arrays, never private attributes, and supports a `strict` mode.
- Rules and rule sets (`rulepy.Rule`, `rulepy.RuleSet`): a rule has a condition
  (`when`), a payload (`then`, constants or value expressions computed from the
  data) and an optional action (`do`). Rule sets apply DMN-style hit policies
  (`HitPolicy`: `FIRST`, `PRIORITY`, `UNIQUE`, `ANY`, `RULE_ORDER`, `COLLECT`
  with per-key `sum`/`min`/`max`/`count`) and return a `Decision` with every
  rule's result and tree, the selected rules, `outputs` and `output`.
  `evaluate()` and `evaluate_many()` are pure; `run()` also calls the actions.
  Rules and rule sets pickle and deep-copy. Decision outputs and aggregates are
  read-only, and aggregates follow the arithmetic rules (Decimal as float64,
  64-bit integer overflow and NaN are null). Semantics: `docs/spec/rules.md`.
- Errors: `RuleDefinitionError`, `HitPolicyError`, `ActionError` (with the
  decision and the actions already run), `RuleNotFoundError` (a `KeyError`);
  `EvaluationError.row` names the input in batches.
- `rulepy.core.evaluate.evaluate_value_tree` and `type_group`.
- Explanations (`rulepy.core.explain`): `Decision.explain()` reports, for every
  rule, whether it was selected, fired without being selected (and why), did not
  fire or is unknown, and its requirement: the conditions behind the outcome,
  grouped as `all` (each must change / each is needed) or `any` (one is enough),
  with the data values they read and structured counterfactuals
  (`short by 200`, `needs total <= 1000 (over by 300)`). The text report is
  ASCII. Suggested fixes are checked against the rule, and conflicting
  conditions are reported as such (`achievable`). `Decision.why_not(name)`
  explains one rule; `Decision.logic` records
  the logic used. `rulepy.core.expr.format_scalar` renders constants.
- `RuleSet.summary()`: a static overview of a rule set (configuration, one line
  per rule, the fields it reads and where, including which outputs depend on
  them, its outputs and tags).
- `Expr.field_paths()`: the fields a condition or value reads, in order.
- `rulepy.errors.format_name`: quotes rule names, tags and keys for reports.
- `rulepy.errors.format_path` renders field paths unambiguously
  (`orders[0].total`, `['x y']`).
- Errors for evaluation and registries: `TypeMismatchError`,
  `MissingFieldError` (both name the field path) and `RegistryError`.
- Condition AST specification (`spec/ast.md`, draft): node catalogue,
  Kleene three-valued semantics, null and type-mismatch rules.
- The package ships a `py.typed` marker.
- Documentation site skeleton (MkDocs Material + mkdocstrings) with the API
  reference for `rulepy.errors` and the conventions shared by every backend
  (`docs/spec/README.md`).
- Development tooling: `dev` dependency group (pytest, pytest-cov, hypothesis,
  ruff, pyright) with strict pytest, branch coverage (>= 90%), strict pyright
  and ruff (Google docstrings) configured in `pyproject.toml`.
