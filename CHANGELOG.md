## [Unreleased]

### Added

- JSON format, version 1 (`spec/json-format.md`), the contract between
  languages: documents with `"version": 1`, the encoding of values (exact
  64-bit integers, floats with `{"$float": "inf"}`, `{"$decimal": ...}`,
  `{"$date": ...}` and `{"$datetime": ...}` with fixed offsets or RFC 9557 time
  zones, lists and maps), every condition node, canonical writing, error codes
  and limits. JSON Schemas in `spec/schemas/v1/`, checked against valid and
  invalid examples. The specification moved from `docs/spec/` to `spec/`.
- JSON format: rules (`name`, `when`, payload `then`, `priority`, `tags`,
  `description`, `metadata`) and rule sets (`hit_policy`, `aggregate`, `logic`,
  `strict`, `rules`), with JSON Schemas and the error codes
  `rule_definition_error`, `registry_error` and `unsupported`. Payload member
  order is significant. Actions are not serialized yet (writers take
  `omit_actions`), and rule metadata values must be data values.
- JSON format: decisions, with every rule's result tree (`truth` for
  conditions, `value` for values), structured reasons and the selected rules;
  outputs are derived from the payload trees. A decision is read with its rule
  set and checked against it node by node (`decision_mismatch`).
- Error catalogue (`spec/errors.md`): stable codes, the hierarchy under
  `CleanRulesError`, and the context fields that conformance vectors compare.
- Conformance vectors (`conformance/`): the vector format and its JSON Schema,
  a checker, 125 hand-picked and 1,821 generated vectors, and 187 vectors for
  reading documents, written from the spec.
- Data model (`spec/data-model.md`): values, decimals of 38 digits (as Arrow
  `Decimal128`), microsecond datetimes, opaque values for native data with no
  equivalent, nulls with a reason (`int_overflow`, the new `decimal_overflow`,
  `read_error`), and how each language's data is read and converted.
- Specification of explanations and summaries (`spec/explain.md`): rule
  status, requirements with `all`/`any` groups, simplification, the check that
  each way to fire really works, counterfactuals and notes. Their JSON forms
  are output-only documents.
- Specification: `matches` patterns use the syntax of Rust's `regex` crate, and
  a null constant is only allowed as the operand of `is_null` (also under
  `and`, `or` and `not`).
- YAML rule files (`spec/json-format.md`, *YAML*): the JSON subset of the YAML
  1.2 core schema, one document, no directives, anchors, aliases or tags,
  errors with line and column, and a 1 MiB default size limit of their own;
  38 new conformance vectors. Rust core: the `yaml` feature (`cleanrules::yaml`
  with `parse` and `to_string`, `format::read_yaml_document` and
  `format::read_yaml_decision_document`), `Limits::max_yaml_size`, and
  `read_parsed_document`/`read_parsed_decision_document` for documents already
  parsed.
- Python binding: `loads`, `load`, `dumps` and `dump` read and write
  conditions, rules and rule sets as JSON or YAML documents, from strings,
  bytes, paths or open files.
- Text syntax for conditions, rules and rule sets (`spec/text.md`):
  `RULE vip PRIORITY 10 IF customer.years > 5 THEN discount = 0.15`, with
  `AND`/`OR`/`NOT` (and `&`, `|`, `~`, as in fuzzytool), comparisons, `IN`,
  `BETWEEN`, `IS [NOT] NULL`, `MATCHES`, `STARTS WITH`, `ENDS WITH`,
  `CONTAINS`, arithmetic, typed literals (`DATE "…"`, `DECIMAL "…"`) and rule
  set headers (`HIT POLICY`, `AGGREGATE`, `LOGIC`, `STRICT`). Errors carry the
  line and column; every condition, rule and rule set without metadata has a
  canonical text that reads back as the same model. Rule files use the suffix
  `.rules` and have a 4 MiB default size limit. 86 new conformance vectors.
  Rust core: `cleanrules::text::{parse, parse_rule, to_string}`, `Display` for
  `Node`, and `Limits::max_text_size` (a new public field of `Limits`).
- Python binding: `format="text"` in `loads`, `load`, `dumps` and `dump`
  (`.rules` files), and `rule_from_text`, which reads one rule and can attach
  an action to it.
- Text of explanations and summaries (`spec/explain.md`, *Text* and
  *Summaries*), generated by the core and the same in every language:
  conditions, names and constants as in the canonical text, data values
  bounded (long strings, lists and maps are cut), gaps as plain numbers, days
  or durations. The canonical text writes a float as plain digits followed by
  `e0` when its magnitude is 0 or within [1e-4, 1e16) (`0.7e0`, not `7e-1`).
  Rust core: `Display` for `Explanation`, `RuleExplanation`, `Cause` and
  `Summary`, fixed by snapshot tests (`insta`); `RuleExplanation::rule` is now
  the rule (`&Rule`), not its name; `Summary::actions` and
  `Summary::with_actions`, which bindings use, and summaries in JSON mark a rule
  with an action (`"action": true`), as the spec said. The explanation and
  summary structs are `#[non_exhaustive]`: only `explain` and `summary` build
  them.
- Decision tables (`spec/tables.md`): inputs, outputs with optional output
  values, and rows whose cells use the text syntax without their column
  (`> 5`, `IN ('ES', 'PT')`, `-`). A table is read and written as a JSON or YAML
  document (`"decision_table"`, added to format version 1 with its JSON
  Schema) and as CSV (RFC 4180; commas, semicolons or tabs; settings lines
  `HIT POLICY`, `AGGREGATE`, `LOGIC`, `STRICT`, DMN letters such as `P` and
  `C+`; `RULE`, `PRIORITY`, `DESCRIPTION` and `THEN` columns), with errors
  located by line and column or JSON Pointer. It compiles into a rule set: the
  new `output_order` policy and `priority` rank rows by their output values, as
  in DMN. Reading a table is bounded by a count of cells and condition nodes
  (`Limits::max_table_size`, 2²¹ by default), since every input cell holds a
  copy of its column. 99 conformance vectors. Rust core: `cleanrules::table`
  (`DecisionTable` with `new`, `from_csv`, `to_csv` and `ruleset`,
  `TableConfig`, `TablePolicy`, `TableOutput`, `TableRow`),
  `Document::DecisionTable` and `format::write_table`. `RuleSet::new` checks
  rule names in `O(n log n)`.
- Python binding: `DecisionTable`, `TablePolicy`, `TableOutput` and
  `TableRow`; `format="csv"` and `.csv` files in `load`, `loads`, `dump` and
  `dumps`, which also read and write tables as JSON and YAML; `table.ruleset`
  (built on first use), `evaluate`, `evaluate_many` and `summary`. Tables are
  immutable and pickle. `load` and `dump` keep line breaks as written in every
  format, on every platform.
- Decision tables from grids (`spec/tables.md`, *Grids*): a header and rows of
  cells, as spreadsheets and data frames hold them. Text cells are read as CSV
  fields, other values as constants (equality under an input), and nodes built
  in a host language as they are; errors point into the grid (`/header/<c>`,
  `/rows/<r>/<c>`). An output cell written as a bare name that is one of its
  column's string values (`high` for `'high'`) gets a hint to quote it. 28
  conformance vectors, with the new `table_grid` input. Rust core:
  `DecisionTable::grid` and `GridBuilder` (`push_row`, `finish`), which build a
  table one row at a time, `DecisionTable::from_grid`, `table::HeaderItem` and
  `table::Cell`.
- Actions by registered name (`spec/rules.md`, *Actions*): a rule may name its
  action (`"do": "notify"` in JSON and YAML, `DO notify` in text), which is
  data: read, written and shown in summaries (`"do"` next to `"action": true`;
  `DO notify` in the text). The core never resolves or runs it. Bindings look
  names up only in a registry the caller supplies, never as import paths; an
  unknown name is a `registry_error` raised before anything runs. `DO` is now
  a keyword of the text syntax: a field named `do` is written `` `do` ``.
  16 conformance vectors. Rust core: `Rule::action_name`,
  `Rule::get_action_name` and `RuleSet::check_action_names`, which every
  binding uses to report an unknown or unbound name the same way.
- Python binding: `Rule(do="notify")` names an action, and `Rule.action_name`
  gives the name; `RuleSet.bind(actions)` resolves names in a mapping of callables,
  and `load`, `loads` and `rule_from_text` take `actions=`. `run` refuses a
  rule set with unbound names before evaluating. Named actions are written
  with their rules; only an action given as code without a name needs
  `omit_actions`. `RuleSummary.action_name` gives the name. A malformed
  registry is a `TypeError`.
- Python binding: `DecisionTable(header, rows, ...)` builds a table from rows,
  and `DecisionTable.from_dataframe` from a pandas or polars `DataFrame`
  (neither is imported; missing values are empty cells). A `str` cell is the
  text syntax, as in the table's CSV. `HeaderItem` types a header. `TableOutput`
  values default to none, and `load`, `loads` and the constructors take
  `max_table_size`.
- C ABI (`crates/ffi`, crate `cleanrules-ffi`, task E.1a): the header
  `crates/ffi/include/cleanrules.h`, generated by cbindgen and checked in CI,
  over a static and a shared library. Opaque handles (`cr_document`,
  `cr_ruleset`, `cr_decision`, `cr_limits`, `cr_error`) owned by the caller;
  texts in as a pointer and a length; documents read and written in JSON, YAML,
  the rule syntax and CSV; rule sets read from a rule set, a decision table or
  one rule; evaluation of a JSON input; recorded decisions read with their rule
  set; outputs, explanations and summaries as JSON, YAML or text. Every
  fallible function returns a `cr_status` and fills an optional `cr_error` with
  the message, the hint and the error's JSON form; misuse names the function,
  and panics become `CR_INTERNAL_ERROR`. `CR_ABI_VERSION` and
  `cr_abi_version()` version the ABI. The conformance vectors that need no
  native values (1,149) pass through it; its tests run under Miri, and
  `docs/examples/discounts.c` under the address and undefined behaviour
  sanitizers.
- C ABI, native values (task E.1b): `cr_value` builds data without JSON, with
  every kind of the data model (nulls with a reason, decimals from their text,
  dates, naive and aware datetimes, lists whose unset positions are null, maps,
  records, and opaque values as a type name and a token the program chooses),
  reads it back with `cr_value_kind`, `cr_value_get_*` and borrowed list and
  map items, and converts it to and from JSON. Values nest at most 1024 deep.
  `cr_ruleset_evaluate_value` evaluates one, with limits; `cr_ruleset_len`,
  `cr_ruleset_rule_name`, `cr_ruleset_hit_policy`, `cr_ruleset_aggregate`,
  `cr_ruleset_strict` and `cr_ruleset_field_paths` (the paths a rule set
  reads) describe a rule set; `cr_decision_len`, `cr_decision_fired`,
  `cr_decision_truth`, `cr_decision_selected_len`, `cr_decision_selected`,
  `cr_decision_output_value` and `cr_decision_outputs_value` read a decision
  without evaluating it again. Every evaluation vector also passes from a
  native value rebuilt with these functions, and their tests run under Miri.
- C ABI, actions, grids, nodes and batches (task E.1c): action registries of
  C functions by name (`cr_actions_new`, `cr_actions_add`), checked with
  `cr_ruleset_check_actions` and run with `cr_ruleset_run`. Each action gets
  a `cr_action_call` (`cr_action_call_decision`, `_rule`, `_input`, and
  `cr_action_call_fail`, whose message becomes the error's cause); a
  `CR_ACTION_ERROR` keeps the decision (`cr_error_decision`, the same handle
  the actions saw) and the rules whose actions had run. `cr_decision_rule_name`
  and `cr_decision_rule_output`. Decision tables from grids (`cr_grid_new`,
  `cr_grid_push_row`, `cr_grid_finish`; after a failed row a grid can only be
  freed); single conditions and values (`cr_node_read`, `cr_node_write`,
  `cr_node_evaluate_tree`, `cr_node_evaluate_value_tree`, with their result
  trees); and batches (`cr_ruleset_evaluate_many`, `cr_batch_len`,
  `cr_batch_get`), which report the first input that fails. Every
  conformance vector now runs through the C ABI.
- Python binding: `RuleSet.read_decision(text, format="json")` reads a
  recorded decision back, checked against the rule set (`decision_mismatch`
  otherwise), as `cr_ruleset_read_decision` does in C (task E.1d); it explains
  and writes like an evaluated one.
- CI builds and runs the C example on Windows with MSVC too (task E.1d).
- C++ (`bindings/cpp`, task E.2a): `cleanrules.hpp`, a header-only C++17
  layer over the C ABI. RAII handles (`ruleset`, `document`, `decision`,
  `batch`, `node`, `grid`, `actions`, `limits`) that move, and values
  (`value`) that also copy; borrowed views (`value_ref`, `decision_ref`).
  Values build from C++ data (`value::map({{"years", 7}})`, dates, opaque
  values) and read back with `as_int`, `as_string`, ... Errors as in
  `std::filesystem`: every call that can fail throws an exception of the
  hierarchy of `spec/errors.md` (`cleanrules::error`, `format_error`,
  `missing_field_error`, ...), or fills an `error_info &` and never throws;
  built without exceptions, only the second exists. Actions are C++
  callables, and one that throws stops the run with an `action_error`
  nested over its exception. Read from a temporary, views are owned copies.
  A CMake package (`find_package(cleanrules)`, targets `cleanrules::c` and
  `cleanrules::cleanrules`) that builds the C library with cargo, statically
  or shared, for the platform CMake builds for (`CLEANRULES_RUST_TARGET`),
  and installs both headers. The
  example `docs/examples/discounts.cpp`; CI builds and tests it on Linux and
  macOS under ASan and UBSan, and on Windows with MSVC.
- C and C++ packages (task E.2b): a Conan 2 recipe
  (`conan create bindings/cpp/conan`, option `shared`) with a `test_package`,
  and a vcpkg overlay port (`--overlay-ports=bindings/cpp/vcpkg/ports`, static
  or dynamic by triplet) with a manifest-mode test. Both build through the
  CMake package, so the build machine needs a Rust toolchain; both give the
  targets `cleanrules::c` and `cleanrules::cleanrules` (C++17 whatever the
  profile's C++ standard). CI builds both on Linux and Windows. The CMake
  package now supports MSVC's static C runtime (`CLEANRULES_MSVC_STATIC_CRT`,
  from `CMAKE_MSVC_RUNTIME_LIBRARY`; Conan's `compiler.runtime=static`,
  vcpkg's static CRT triplets), derives iOS targets, and hands cargo the C
  compiler as linker when building for another platform. Without cargo, CMake
  now says to install it with rustup.
- C++ conformance runner (task E.3): the ctest test `conformance` runs every
  conformance vector through `cleanrules.hpp` twice, as `json:<id>` (JSON
  entry points and the throwing overloads; `read` vectors also with
  `error_info`) and `native:<id>` (inputs built with the value constructors,
  the `error_info` overloads, and decisions read back with the decision
  readers), comparing with a lossless JSON parser of its own. Under
  `CLEANRULES_SANITIZERS`, any AddressSanitizer report fails a test, and so do
  leaks on Linux.
- Idiomatic JavaScript API (task F.2a), the root of the `cleanrules` npm
  package, the same in the Node addon and the WebAssembly build: conditions
  built with the `F` proxy and methods (`eq`, `ne`, `lt`, `le`, `gt`, `ge`,
  `and`, `or`, `not`, `add`, `sub`, `mul`, `div`, `neg`, `abs`, `isIn`,
  `between(low, high, { closed })`, `isNull`, `matches`, `startsWith`,
  `endsWith`, `contains`; fuzzytool's `&`, `|` and `~` are `.and()`, `.or()`
  and `.not()`), the functions `field(...path)`, `constant(value)`, `and`, `or`
  and `not`, and immutable `Expr`, `Field` and `Const` nodes (`tag`, `kind`,
  `children()`, `walk()`, `fieldPaths()`, `sameAs()`, `toString()` with the
  canonical text, `toJSON()` with the node's JSON form, `path`, `value`;
  assigning to one is a `TypeError`), built by the core's constructors so that
  a bad node fails at once with an `ExpressionError`. The proxy never makes a field thenable (`then`), keeps
  symbols, `toJSON`, inspection and methods as members, reaches keys named like
  methods and indices with `.at(...)` or `field(...)`, and refuses `F.items[0]`
  (ambiguous in JavaScript) and JavaScript operators on nodes (`F.age >= 18`)
  with an `ExpressionError` naming the fix. `Rule` (name, condition, payload,
  `priority`, `tags`, `description`, `metadata` and `do`, a function or an
  action's name) and `RuleSet` (`hitPolicy`, `aggregate`, `logic`, `strict`;
  iterable, `length`, `rules`, `get` (`undefined` for an unknown name, like
  `Map`), `has`, `rule` (a `RuleNotFoundError` listing the rules),
  `fieldPaths()`, `evaluate`, `evaluateMany`, `readDecision`, `bind(actions)`,
  `run(data)` and `summary()`), with Python's checks and errors (an unknown
  option is a `TypeError`; `toJSON()` of rules and rule sets is an
  `UnsupportedError` until they can be written). `Decision`
  (`ruleset`, `results`, `selected`, `fired`, `hitPolicy`, `outputs`,
  `output`, `aggregated`, `explain()`, `whyNot(name)`, `toJSON()`) gives
  native values, and opaque values as the very objects read. `run` calls the
  selected rules' actions with an `ActionContext` (`rule`, `data`, `result`,
  `output`, `decision`), refuses unbound names first, and stops with an
  `ActionError` (with `cause`, `executed` and the decision) when one throws or
  returns a promise. Explanations and summaries are frozen objects of the
  classes Python has (`Explanation`, `RuleExplanation`, `Cause`, `CauseGroup`,
  `Counterfactual`, `Note`, `Reason`, `Summary`, `RuleSummary`, `FieldUsage`,
  and `RuleResult`), with the core's text as `toString()` and its JSON
  documents as `toJSON()`. `ZonedDateTime`, the aware datetime given back:
  local fields, `offsetSeconds`, `timeZone`, `epochMicroseconds`, `toDate()`,
  `toTemporal()` and the RFC 9557 text; it reads back as input. What the core
  cannot hold (a forged marker, an instant beyond its range) is opaque and
  comes back as the object read. Each build makes its own API classes; passing
  an object to the other build is a `TypeError` that says so. TypeScript
  declarations with literal types (`HitPolicy`, `Aggregate`, `Truth`, `Status`,
  `Kind`, `Closed`, `Tag`, `NoteKind`, `GroupKind`, `CompareOp`, `ReasonCode`),
  a typed `F` whose `then` is `undefined` and whose indices are `never`, and
  `Fields<T>` (`F as Fields<Order>`: checked keys, nothing possibly `undefined`
  under `noUncheckedIndexedAccess`); tests on both builds, in Node and Deno,
  comparing the builds' errors, outputs, explanations and summaries; the example
  `docs/examples/discounts.mjs`. The native layer, `cleanrules/native`, does
  not change; both builds gain internal functions that build nodes, rules and
  rule sets and give values back in a private encoding shared by the two.
- WebAssembly build of the JavaScript binding (task F.1b): the same npm
  package `cleanrules` runs in browsers, Deno (2.6 or later) and other runtimes
  on a WebAssembly module built with wasm-bindgen, with the same API as the
  Node addon (`cleanrules` and `cleanrules/native`: the same classes, methods,
  options, errors and their messages, markers and `ActionCall`).
  `package.json` `exports` picks the build: `node` loads the addon; `deno`
  imports the module as a module source, with no permission
  (`index.deno.js`, `native.deno.js`); `browser` and `default` fetch it by URL
  (`index.wasm.js`, `native.wasm.js`, which use no Node API). The module,
  also exported as `cleanrules/wasm/cleanrules_bg.wasm` for bundlers, is
  1.8 MiB, 643 KiB gzipped; `npm pack` refuses a missing or stale one. On Node
  without a prebuilt addon, `--conditions=browser` runs it. The package is now
  ES modules, one copy of the shared code; CommonJS still works on Node
  through `require(esm)`, and TypeScript compiling to CommonJS needs
  `"module": "nodenext"`. The Rust crate, renamed `cleanrules-js`, has one
  shared module and two thin front ends chosen by target (napi-rs on native
  targets, wasm-bindgen on `wasm32`), which check arguments the same way.
  Differences: the module's objects also have wasm-bindgen's `free()`; a
  second release does nothing and a released object is a clear `TypeError`.
  The test suite runs on both builds in Node and on the module in Deno, and
  compares the builds' members and errors; CI adds a job for it, with wasm32
  clippy and `wasm-bindgen` pinned to the crate's version. Changes to the Node
  build: arguments of the wrong kind (a text, an options object, a rule
  position, a document) are `TypeError`s with the binding's own messages, the
  classes' constructors throw a `TypeError` that says where objects come from,
  `[Symbol.dispose]()` does nothing, the engine's own objects passed as data
  are opaque, and built-in objects are told apart by brand and tag in any
  realm (array and string iterators are now opaque like the other iterators).
- Node binding (`bindings/js`, npm package `cleanrules`, task F.1a): the
  engine as a native addon built with napi-rs, for Node 22.12 and later (N-API
  9), with one optional package per platform (`@cleanrules/node-<platform>`:
  Linux x64 and arm64 with glibc and musl, macOS x64 and arm64, Windows x64 and
  arm64); the package refuses an addon of another version. The native layer is
  `cleanrules/native`: `Document`, `RuleSet`, `Decision` and `Node` read and
  write JSON, YAML, the rule syntax and CSV (`{ format, limits }`, with
  `maxSize`, `maxNesting`, `maxDepth`, `maxTableSize`, `maxYamlSize`,
  `maxTextSize`), evaluate native JavaScript data or JSON values, one input or
  a batch, read recorded decisions, explain and summarise (as text by default,
  as in C++), and evaluate single condition and value nodes
  (`{ logic, strict }`). `run(data, actions)` calls the selected rules' named
  actions as synchronous JavaScript functions with an `ActionCall` (`ruleName`,
  `position`, `input`, `truth`, `outputJson`, `decision`); one that throws or
  returns a promise stops the run with `ActionError`. Native data is read as
  `spec/data-model.md` says for JavaScript (only the paths the rules read, each
  object and getter once, getters but never methods, prototypes, symbols or
  `#` fields; `Map`, typed arrays, `Date` and Temporal values; bytes opaque).
  `cleanrules` itself exports what is final: `decimal`, `float`, `date` and
  `datetime` for the kinds JavaScript lacks (branded with
  `Symbol.for('cleanrules.marker')`), `FORMAT_VERSION`, `version`, and the
  errors, `CleanRulesError` and its subclasses, with `code`, `hint`, `context`,
  `cause` (what a getter or an action threw) and `toJSON()`. Outputs and
  explanations come out in the JSON format. TypeScript declarations with
  literal types (`Format`, `HitPolicy`, `Aggregate`, `DocumentKind`, `Truth`),
  tests with `node:test` (`npm --prefix bindings/js test`), a CI job on Linux,
  macOS and Windows with Node 22, 24 and 26 that also checks that every version
  matches, a workflow that builds and tests the release addon on every
  platform, and the example `docs/examples/discounts.js`.
- C ABI: `cr_value_clone`, a deep copy of a value that keeps null reasons and
  opaque tokens, and `cr_decision_clone`, which keeps a decision borrowed from
  a batch, an action call or an error.
- Core: `TableConfig::from_names` (a grid's settings by name, with a hint
  listing the valid names, now also used by Python) and `text::parse_node`
  (one expression of any kind).
- Data model (`spec/data-model.md`): the C value builder makes opaque values
  from a type name and the program's token, never from a C pointer with a
  release callback, and refuses dates, datetimes and offsets a value cannot
  hold; a time zone is kept only under the exact spelling of the bundled
  database (`AwareDateTime::from_native`, also in Python).
- Core: `Decision::selected_positions`, which the Python binding now uses.
- Errors (`spec/errors.md`): a stable number per code for C (*Numeric codes*)
  and a stable JSON form of every error (*JSON form*, with the JSON Schema
  `spec/schemas/v1/error.schema.json`), written by
  `cleanrules::format::write_error`.
- Formats (`spec/json-format.md`, *Documents*): which documents each format
  holds, and a rule set from any document: a rule set, a decision table's, or
  a rule set of one rule with the default settings.
- Core: `format::DocumentFormat` with `read_document_as` and
  `write_document_as` (any format from bytes; text that is not UTF-8 is a
  `format_error` at the first invalid byte, in every format), `parse_as`,
  `read_decision_document_as`, `write_decision_as`, `write_explanation_as`,
  `write_summary_as`, `Document::into_ruleset`, `json::utf8_text` and
  `Limits::with_max_size`, so that every binding reads and writes formats the
  same way. The Python binding uses them.
- Python binding: `str()` of an `Explanation`, a `RuleExplanation`, a `Cause`
  and a `Summary` gives that text, and `str()` of a condition its canonical
  text (`x > 5 AND NOT vip`; `repr()` is still the Python that builds it).
  `RuleSummary.action`, and `Summary.to_dict()` marks rules with an action.
  The text is made on first use, so `explain()` costs nothing more.
- Python binding, safety: frames, tracebacks, code objects, generators,
  coroutines and functions in the data are opaque; a rule can no longer reach
  the program's globals or locals through them. Decisions in reference cycles
  are freed by the garbage collector. `ActionContext.tree` gives the result
  tree of the rule's condition.
- Rust core and spec: a read error met in the middle of a path gives
  `read_error` (and raises in strict mode) instead of an ordinary null;
  `Error::unsupported` sets `operation` and `reason`.
- Python binding: `evaluate_tree` and `evaluate_value_tree` evaluate one node
  and return its `ResultTree` (`spec/ast.md`, *Evaluating one node*).
- Python conformance runner: every vector runs through the binding's JSON
  entry points and, except the `read` vectors, with native Python data and the
  Python API; all pass.
- Python binding: actions (`Rule(..., do=...)`) and `RuleSet.run`, which runs
  the actions of the selected rules in order with an `ActionContext` and stops
  at the first that raises with `ActionError`. `Rule` and `RuleSet` pickle and
  copy. The public API is fully typed (`pyright --verifytypes`).
- Python binding: numpy and pandas values: numpy scalars, `datetime64` (a
  naive datetime, truncated to the microsecond), arrays as lists, `NaT`,

### Changed

- The license is now the Apache License 2.0 (it was MIT), with a NOTICE that
  names Jose L. Salmeron as the author and that every redistribution, and
  every derived work, must keep (section 4(d) of the license).
- Data model (`spec/data-model.md`): an entry of a native map whose key is not
  a string is left out (it was "made opaque", without saying under which key;
  Python already left it out); a list has no missing elements, so holes and
  `undefined` elements of a JavaScript array are null; in JavaScript, every
  `number` that is not a safe integer is a float, infinities included, and
  `Uint8Array`, `Buffer`, `ArrayBuffer` and `DataView` are opaque like bytes in
  other languages. Native data only, so no conformance vector changes.
- Data model (`spec/data-model.md`, *JavaScript and TypeScript*): values given
  back to JavaScript are specified (*Values given back*): null of any reason as
  `null`, ints as `number` within ±(2⁵³ − 1) and `bigint` beyond, floats as
  `number`, decimals as `cr.Decimal` with the canonical text, dates and naive
  datetimes as `cr.LocalDate` and `cr.NaiveDateTime`, aware datetimes as the
  new `cr.ZonedDateTime` (with `toTemporal()` in its zone or at its offset, a
  `RangeError` for an offset with seconds), lists as arrays, maps as plain
  objects (a key such as `__proto__` an own property), opaque values as the
  objects read (`null` in a decision read from a document); counterfactual
  gaps and priorities by the same rules. Each reads back as the same value,
  except the keys `__proto__` and `constructor` of a plain object, an opaque
  given back as `null`, and a float holding an integer; payloads and outputs
  are frozen shallowly. `cr.ZonedDateTime` is a new input row. Native data
  only, so no conformance vector changes.
- Data model (`spec/data-model.md`, *JavaScript and TypeScript*): objects of
  the runtime (`Error`, `Set`, `WeakMap`, `WeakSet`, `WeakRef`,
  `FinalizationRegistry`, `Promise`, `RegExp`, boxed primitives, iterators,
  generators, module namespaces, and the binding's own objects) are opaque,
  recognised by brand or by `Symbol.toStringTag`; they were "anything not
  listed". Native data only, so no conformance vector changes.
- Errors (`spec/errors.md`): in JavaScript the context fields are in `context`,
  because an error's `name` is its class, and an `ActionError` has the
  `decision`.
- The Conan recipe also exports the Node binding's crate (manifest, build
  script and sources), now a member of the workspace that cargo loads.
- The conformance vectors of `registry_error` for an unknown logic in a table
  or in text list the `name`, which `spec/errors.md` marks as compared.
- The text syntax reserves `DO` (task D.4): a field, key or rule named `do`,
  in any case, is now written between backticks or quotes.
- `Summary::with_actions` adds the rules whose action is code to those that
  name theirs, which the core marks itself, instead of replacing every flag.
- Strict-mode errors write a field's path as the text syntax does
  (`missing field items[2].price`, not `items.[2].price`), as explanations
  already did (task D.5).
